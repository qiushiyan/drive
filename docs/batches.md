# The batch record and wakes

A batch is the sessions one driver drives together, usually a night's work, and the record of everything done to them. It is what a driver with no memory between runs (the chat bot is woken fresh each time) reads to know where things stand, and what the owner reads on the page whenever they choose to look. `docs/sessions.md` is how each action on a session works; this doc is what those actions leave behind, how the driver is brought back, and how the owner reads it.

## The record

Each batch is a directory under the state directory (`~/.local/state/drive/batches/<name>/`; `DRIVE_STATE_DIR` moves it):

- **`batch.json`:** settings fixed when the batch starts: its driver, how that driver is woken and the webhook that wakes it, the Rex session new blocks open in (started with the batch if none runs), the zone times are shown in, the commands run after each wake.
- **`events.jsonl`:** the append-only log, one event per line, written whole.
- **`sends/`:** each file a session was told to read, saved before it was told and never overwritten, so what a session read stays as it was.
- **`watches.log`:** what each watch printed, so one that ended early says why.

What is true now is derived from the log and never written separately (`internal/batch/events.go`): which sessions belong to the batch and under which label, which are parked and why, who holds what and who waits for it, which asks are open. A fact with a second home drifts from the first.

## Drivers and their batches

Several drivers share the mini, each a chat bot woken by its own webhook or a session that waits itself, and each drives a batch of its own. A batch belongs for good to its driver: the one its webhook names, which is the name a chat driver is known by, or the one `--driver` names when a driver that waits itself starts it; a batch started with neither belongs to a driver of no name (`batch.DriverOf`). Which batch each driver drives now is the state directory's lifecycle log, `drivers.jsonl` (`internal/batch/drivers.go`): a batch becomes its driver's current one when it starts or is used, and stops being live when it ends or another of its driver's replaces it. The live batches are the drivers' current ones. A store an older drive kept, with its one `current` link, carries that link over to the driver its batch names, once. Every driver shares one state directory, rather than each keeping its own, because the per-block locks and the owner's page must see them all.

A command acts in one batch, resolved once for the run (`Driver.Batch` in `internal/drive/driver.go`): the one `--batch` pins, else the current batch of the driver `--driver` names, else the current batch of the driver of no name, but only while no named driver drives one. Where named drivers drive, a command that names none is refused with the command again for each driver (`nameYourself`), never run in a driver's batch by default: nothing in a chat bot's shell says which bot runs a command, so a default would put a bot's records and wakes in another bot's batch whenever it forgot to name itself. A `--batch` that is another driver's than `--driver` names is refused too. A watch carries its batch by name, so a wake from an old batch never acts in a new one.

`batch new` replaces only its own driver's batch, and stops that one's watches and timers, since they would wake the driver about sessions it now drives in the new one; another driver's batch is never touched. `batch use` makes an older batch its driver's current one again, and `batch end` ends one whose drive is over and whose record the owner has read: its wakes stop and it leaves the page. A watch is named for its batch with the name's punctuation read as dashes, so a name that would read as another batch's there is refused, since ending one batch would stop the other's watches. A taken name is refused before the start runs a Rex session or writes anything; a webhook that holds no URL yet does not stop it (§ Wakes). A new batch starts with no grants: authority the owner handed over lives as long as the batch it was given in.

## Intents and settling

A send or an open records an intent under the batch's lock before its first effect, and its outcome after; a first step that goes behind the notice records the notice's intent beside its own, so the step stays unsettled until it goes. An intent with no outcome means its driver still owns the session (`docs/sessions.md` § One driver at a time) or has gone, often a chat driver whose shell timed out mid-send. The next driver to send, respond, park or close on the session settles it from the transcript: its own line arriving after the intent makes it `arrived`; another prompt makes it a failure naming what arrived instead; none, a failure that never reached the session. Time never decides it, since a legitimate send can take minutes to confirm, and an unreadable session decides nothing either: settling then refuses the action, to be tried again, and leaves the intent unsettled, since a step that arrived and still runs would otherwise read as one that never reached the session and free its hold (`settle` in `internal/drive/settle.go`). A session gone or closed holds nothing, and settles from what it shows. `status` lists an unsettled intent with the driver acting on it, or as left by one that has gone.

`open` records its block the moment Rex opens it, before Claude Code has started, so a driver that ends mid-launch leaves the block on record; an open whose driver left no block on record is settled by looking for a block under its label that no other live batch drives, since another driver's batch may open one under the same label.

## Holds

A hold is a name for something only one session may do at a time: a release, a closeout into a shared checkout, commits into a checkout others edit. `send --hold NAME` takes it when the send is admitted, under the batch's lock, so no other send can take it meanwhile. It stays held while that send is under way, while its holder works, a later step included, since a follow-up to a closeout is still the closeout, while it waits on a prompt, and while background jobs it started run: a step such as merge-when-ready ends its turn waiting on checks in a background job, and the merge comes after. While the holder's session cannot be read the hold stands; a holder that is gone or closed frees it. A refusal on a hold says which keeps it, and its `next:` what frees it from there (`holdNext` in `internal/drive/holds.go`): the holder's turn ending, its prompt answered, or its job ending, with the step that has the holder stop a job that should have ended.

`open --hold` checks its hold before it opens a block. A send or an open refused on a hold is recorded with its step, so `status` lists each waiter and what it was refused (`Waiting`), and the holder's wake names each with the send or open to run once the hold is free; sending to it clears that. A parked waiter wakes no one of itself: `drive watch --due` arms it once its hold is free.

## The owner's records

Besides what drivers did, the log keeps what the owner said that grants or decides something, and what the owner is told each session is for (`drive record`):

- **Grant:** authority handed over, in the owner's words and with what it covers.
- **Ask:** a question put to the owner, with the recommendation and what happens while nobody answers.
- **Answer:** whether the owner took the recommendation, amended it, handed it to a fresh model, or it stopped mattering, and whether they needed it explained first.
- **Note:** what a driver wants the next run to know.
- **Goal:** what a session sets out to solve, one plain paragraph for an owner who remembers the product but not the session. It belongs to the label, the latest standing: an open's `--goal` rides on its intent and stands once the block opens, so a failed open or relaunch leaves the label's goal as it was, and `record goal` revises it or gives one to a session drive did not open. Nothing derives a goal, since a session's title and first prompt name only the file it was told to read; `drive status` names the open sessions without one, and `drive read` prints a session's, so a driver writing about it tells the owner the goal the page shows. The goal is the one fact on the owner's page that live reads cannot supply.

`drive metrics` measures a batch from the record, in the terms drivers are compared on: owner wait per merged change, an open ask counted to the batch's end; how often a recommendation was taken; the owner's snippets against typed slash commands and the driver's own words; deliveries that ended garbled, other or unknown; refusals by kind; wakes no action followed; and turns left unwatched, a send or respond that reached a session with no wake, park or close after it, which is the measure of a lost wake. A merged change is every pull request a session linked, counted once however many sessions name it, or, for a session with none, its work once it is in the trunk, as a personal tool's closeout merges it (`landed` in `internal/drive/metrics.go`). The work is the session's newest commit, found by the subject and time `claude-steps` saw it with, since a closeout often removes the branch itself and the commit outlives it; without one, its branch, the newest other than the trunk among those the transcript names and those checked out where it committed. gwt judges either. A measure whose progress lookups failed says so.

## The owner's page

`drive page` serves the live batches as their owner reads them, from the phone, at moments they choose: nothing is pushed, and no model runs to write it. Each session shows its goal, where it stands, the pull requests it opened apart from those it only named (`claude-steps` marks which), when and why the driver parked it, and its last step. The questions waiting on the owner from every batch come first, each linked to its session's card and back, then each batch's sessions under a heading naming its driver, its closed sessions last; `--batch` or `--driver` serves one batch alone. A card is anchored by its batch and label, and a question by its batch and id, since every batch numbers its asks from A1, so a message about one session links it (`…:8444/#2026-10-27/S1`). Sessions are grouped by what was read, never by a claim that their work is done, since no record makes one: waiting on a prompt someone answers, waiting for its next step (a turn ended, an interrupt, an API error, a rejected login), parked, working, not read live, closed. A park is the driver's words at the time it parked, so the page dates it beside what has been read since. The bot still explains; the page shows state.

The page is a third printer of a batch beside text and `--json` (`internal/drive/overview.go`, `page.go`): a read of a batch reads its log once, so a batch started meanwhile is never spliced in, then reads its open sessions as status does (`memberRows`), the closed ones' steps from their transcripts, and every pull request named. One reader, `prStates`, reads the pull requests status, the page and metrics each need, once per pull request however many sessions name it. `claude-steps` and `gh` lookups are killed after 30 seconds, so a hung one fails a row rather than the command; Rex calls are not, since they sit in the send path.

Serving (`internal/drive/serve.go`) is shaped by those costs and by Rex calls that can hang. A visit resolves the live batches once and reads them at once, each on its own reads and deadline, so one slow or unreadable batch keeps none of the others off the page. One read of a batch runs at a time and is reused for 30 seconds from when it ended. A visit waits for what is left of the running read's 20 seconds, then is answered from the record alone (goals, asks, parks, closed sessions), as it is when Rex cannot be read; a read still running after 2 minutes is left to finish, and the next visit starts another. The server exits once an install replaces its binary, for its supervisor to start the new one.

On the mini the dotfiles' launchd agent `com.qiushi.drive-page` keeps it listening on `127.0.0.1:8792`, with a PATH that reaches `rex`, `claude-steps` and `gh`, and `tailscale serve` publishes it on the company tailnet at `https://qiushi-mini.tailf7adf1.ts.net:8444`. Anyone on the tailnet can open it, by the owner's choice; it only reads.

## Wakes

A batch started with `--webhook DRIVER` drives for a chat bot that runs only when woken, so the rule is that a session an action touched is watched: whatever a `send`, `open` or `respond` typed or pressed into a session arms its wake when the action ends, whatever came of it (`docs/sessions.md` § One driver at a time). A refused action touched nothing and arms nothing; its `next:` says what to do instead, which for a session left waiting is to park it. `drive watch` arms one by hand and `drive timer` a timer, such as the veto window on a plan. A batch started without a webhook has a driver that waits itself, with `drive wait`.

A watch is `drive notify LABEL`, and a timer `drive ring SECONDS NOTE`, hidden commands running as a process in a session of its own, with a pidfile under the state directory's `watches/`, named for its batch and session, that holds its pid, the process's start and its command line (`internal/drive/watches.go`); it counts as running only while they all match, so a reused pid is never taken for it. It is not a tmux session: a chat driver's shell commands end, and a tmux server exits taking every session in it along, so a watch outlives both. The wait ends when the turn has stayed over, or on a prompt, for a minute; at once on an API error or an interrupt; ten minutes after a turn that ended while background jobs it started still run, since such a turn usually resumes when they finish, the wake then saying to watch it again; and as gone after three unreadable looks in a row, one being Rex busy for a moment.

Then the watch retires, removing its pidfile, before it posts: a step sent while the post is under way arms a fresh watch rather than counting on one that is about to exit. It records `posting` before its first try, since retries can take ten minutes, then every attempt, so an empty log line is never taken for a wake that arrived. The post carries the session's label, how its turn ended, the end of its reply, the sessions waiting on a hold it held, the view to act on, and a `next:` line, last, where the ending decides what to do. Only a wake that was posted runs the batch's after-wake commands, such as archiving the chat it went to, each killed after two minutes; their failure is noted without failing the wake.

A watch re-execs drive by path, so an install swaps the binary under it: one already running keeps its old code, and a command line an older drive runs after the install, such as the watch a send armed mid-install or the `drive watch --sleep` an older wake printed, is rewritten to this drive's (`upgrade` in `cmd/drive/main.go`).

A watch that ends without posting records why, a kill from anyone but drive included: drive's own stops (`park`, `close`, `drive watch` restarting a stuck watch) remove the pidfile before they signal, and a signalled watch whose pidfile is still there records the kill.

`status` reads each session's wake liveness first, the process table for whether its watch runs and the log for what came of the last one: armed; stuck, a watch still running fifteen minutes past the later of the turn's end and its arming; posting; woken (nothing done since), a wake that wants a decision; none, or ended without a wake; parked. `drive watch --due` is a chat driver's watchdog in one command: it arms every session that has no wake and needs one — never watched, acted on with no wake armed, a watch that died or is stuck, a session that moved on by itself since its last wake (a usage limit's reset continues a turn so), a parked waiter whose hold is free — and posts once more, ten minutes on, a wake nothing was done about, never twice for one view. Until then `status` and `--due` say when it comes, and the wake that comes says it is posted again, since a run waiting on a repost, or one meeting it, decides on that.

Each webhook batch names its driver's webhook, a file under `~/.config/drive/webhooks/`, mode 0600, with a `URL=` and an `AUTH=` line (`internal/config/config.go`), kept outside the repository and the batch. Two drivers on one machine so never wake each other. A batch starts before the owner has written its webhook, since its driver is known by the name: until the file holds a URL no wake or timer arms, since every wake would fail unseen, so each action that would arm one fails saying where the URL goes, and `drive watch --due` arms what is due once it is written.
